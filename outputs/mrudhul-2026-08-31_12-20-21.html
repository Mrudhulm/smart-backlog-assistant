Project Executive Summary

The Smart Backlog Assistant is a Dockerized AI developer tool using Google Gemini and Pydantic type validation to automatically convert unstructured engineering meeting notes and PRDs into structured Agile user stories with Gherkin acceptance criteria and risk analysis.

User Stories (4)

US-001
Priority: High Points: 3

CLI Input Document Ingestion

Story: As a developer, I want to pass text or markdown requirement files via CLI parameters so that unstructured project notes can be processed by the tool.

Acceptance Criteria:

  • Given a valid file path provided via the --input CLI flag, When main.py executes, Then the content is correctly read from the mapped inputs directory.
  • Given a non-existent input file path, When the tool executes, Then an informative error message is displayed and execution terminates cleanly.
US-002
Priority: High Points: 5

Gemini Integration with Strict Pydantic Schema Validation

Story: As a product manager, I want the AI engine to generate user stories backed by strict schema validation so that output JSON files are always 100% reliable and valid.

Acceptance Criteria:

  • Given raw requirement text sent to Google Gemini, When the response returns, Then validator.py enforces strict compliance with the Pydantic schema.
  • Given an invalid JSON payload returned by the AI provider, When validation fails, Then the tool raises a validation error without saving corrupted outputs.
US-003
Priority: Medium Points: 3

Automated Technical Risk & Edge Case Identification

Story: As an engineering lead, I want the system to flag potential technical hurdles and architectural risks so that engineering teams can mitigate them early.

Acceptance Criteria:

  • Given raw engineering notes analyzed by the AI, When user stories are generated, Then an array of technical and architectural risks is included in the output JSON.
  • Given security or performance concerns in the input text, When processed, Then those specific concerns are highlighted in the identified_risks list.
US-004
Priority: High Points: 3

Docker Containerization & Volume Mapping

Story: As a developer, I want to run the application inside a Docker container so that I can execute the tool without local dependency conflicts.

Acceptance Criteria:

  • Given a Dockerfile in the project root, When docker build is executed, Then a clean image based on python:3.11-slim is built with all requirements installed.
  • Given docker run executed with local volume mounts and GEMINI_API_KEY environment variable, When processing completes, Then result.json is written to the host outputs folder.

Identified Technical Risks

  • API key exposure if users log environment variables or container shell history insecurely.
  • LLM output schema failure or invalid JSON generation when handling unusually formatted or very long raw inputs.
  • Input file size exceeding LLM token context limits during execution.
  • File permission or path mapping issues when running Docker volume mounts across different host operating systems.
